# План оптимизации

## Главная опасность

Оптимизация — самый надёжный способ **создать** систему, которая прекрасно выглядит
на истории и не работает вне её. Всё, что описано ниже, устроено так, чтобы этому
мешать, а не помогать.

## Фитнес-функция

`GetFitness` в боте вызывает `FitnessCalculator`, а не возвращает чистую прибыль.

```
fitness = качество × множитель_штрафов × 1000
```

**Качество** — взвешенное ГЕОМЕТРИЧЕСКОЕ среднее семи составляющих:

| Составляющая | Вес | Насыщение |
|---|---|---|
| Матожидание (R) | 0.25 | 0 → 0.35R |
| Profit factor | 0.15 | 1.0 → 2.0 |
| Sharpe-подобный | 0.12 | 0 → 0.35 |
| Sortino-подобный | 0.12 | 0 → 0.50 |
| Recovery factor | 0.10 | 0.5 → 5.0 |
| Качество просадки | 0.16 | 40R → 5R |
| Достаточность выборки | 0.10 | 30 → 300 сделок |

Геометрическое среднее выбрано намеренно: набор параметров с прекрасной прибылью и
катастрофической просадкой **не должен** обгонять сбалансированный. При арифметическом
среднем одна сильная составляющая топит слабую.

**Штрафы** умножаются и способны обнулить результат:

| Условие | Действие |
|---|---|
| Матожидание ≤ 0 | fitness = 0 |
| Без лучших 5% сделок матожидание ≤ 0 | ×0.25 |
| Концентрация прибыли > 60% | до ×0.3 |
| Серия убытков > 12 | до ×0.5 |
| Просадка > 25% | до ×0.2 |
| При росте издержек остаётся < 50% матожидания | до ×0.1 |
| > 70% прибыли из одного инструмента | до ×0.4 |
| Сделок < 30 | fitness = 0 |

## Что оптимизировать

**Мало параметров.** Каждый добавленный параметр экспоненциально увеличивает
пространство поиска и линейно — вероятность найти в нём случайный пик.

### Раунд 1: порог преимущества (3 параметра)

Определяет, насколько система разборчива. Самый влиятельный набор.

| Параметр | Диапазон | Шаг |
|---|---|---|
| `BaseMinimumEdgeR` | 0.00 … 0.30 | 0.05 |
| `EdgeConfidenceZ` | 0.0 … 2.0 | 0.5 |
| `MinRewardToRisk` | 1.0 … 2.5 | 0.25 |

### Раунд 2: выходы (4 параметра)

Часто именно выходы, а не входы, определяют результат (раздел 128).

| Параметр | Диапазон | Шаг |
|---|---|---|
| `AtrStopMultiple` | 1.0 … 3.0 | 0.2 |
| `Target1R` | 0.8 … 2.0 | 0.2 |
| `BreakEvenTriggerR` | 0.5 … 1.5 | 0.25 |
| `TrendTrailAtr` | 1.5 … 3.5 | 0.25 |

### Раунд 3: пороги сигнала (3 параметра)

| Параметр | Диапазон | Шаг |
|---|---|---|
| `MinRegimeConfidence` | 0.40 … 0.75 | 0.05 |
| `MinEnsembleConfidence` | 0.45 … 0.75 | 0.05 |
| `MaxSingleStrategyWeight` | 0.25 … 0.50 | 0.05 |

### Что оптимизировать НЕЛЬЗЯ

| Параметр | Почему |
|---|---|
| `HardMaxRiskPerTradePercent` | Это предел безопасности, а не настройка производительности. Оптимизатор всегда захочет его поднять. |
| `DailyLossLimitPercent`, `WeeklyLossLimitPercent` | То же самое. |
| `MaxDrawdown*Percent` | То же самое. |
| `MaxWinStreakRiskMultiplier` | Оптимизатор найдёт, что мартингейл «работает» на исторической выборке. |
| `PriorStrength` | Определяет, насколько система скептична к малым выборкам. Оптимизатор снизит его, чтобы быстрее «выучить» шум. |

Эти значения выставляются исходя из того, какой риск приемлем, и остаются
зафиксированными во всех прогонах.

## Поиск плато, а не пика (раздел 136)

```
Плохо:                          Хорошо:
   fitness                         fitness
      │        ▲                      │     ▄▄▄▄▄▄▄
      │        │                      │   ▄▄       ▄▄
      │  ──────┴──────                │ ▄▄           ▄▄
      └─────────────── параметр       └─────────────────  параметр
   единственный пик                 устойчивая область
   = подгонка                       = вероятно, реальный эффект
```

После оптимизации в cTrader:

1. Отсортировать результаты по fitness.
2. Взять **топ-20**, а не топ-1.
3. Посмотреть, образуют ли их параметры компактную область.
4. Если да — взять **центр области**, а не лучшую точку.
5. Если нет (лучшие результаты разбросаны) — **преимущества нет**, это шум.

Пятый пункт — самый важный и чаще всего верный.

## Проверка чувствительности (раздел 137)

Для выбранного набора параметров прогнать со сдвигом каждого:

```
−30%  −20%  −10%   базовый   +10%  +20%  +30%
```

```
Если сдвиг любого параметра на 10% рушит результат,
результат был не свойством системы, а свойством этой точки.
```

Практический критерий: при ±20% по каждому параметру fitness не должен падать более
чем на 30%.

## Перенос на другие инструменты (раздел 138)

Параметры, оптимизированные на BTCUSD, прогнать **без изменений** на ETHUSD, SOLUSD,
XRPUSD.

Цель — не использовать их там, а проверить обобщаемость:

```
Работают везде             → вероятно, найдено что-то реальное
Работают только на BTC     → найдены свойства выборки BTC
Работают только на одном   → подгонка
```

Признаки нормированы (проверено тестом масштабной инвариантности) именно затем, чтобы
такой перенос был осмысленным.

## Перенос между режимами (раздел 139)

То же самое по периодам: параметры, найденные на бычьем рынке, прогнать на медвежьем
и боковом. Резкая деградация означает, что оптимизирован конкретный режим, а не
система.

## Протокол оптимизации

```
1. Зафиксировать лимиты риска (не оптимизировать)
2. Оптимизировать раунд 1 на IN-SAMPLE
3. Отобрать топ-20 → найти плато → взять центр
4. Проверить чувствительность ±10/20/30%
5. Проверить на VALIDATION
6. Если деградация > 30% → вернуться к шагу 2 с меньшим числом параметров
7. Повторить для раундов 2 и 3
8. Walk-forward (документ 08)
9. Монте-Карло (документ 09)
10. HOLDOUT — один раз
```

## Сколько прогонов достаточно

Правило: число оптимизируемых точек должно быть **много меньше** числа сделок в
выборке.

```
Если оптимизация перебирает 5000 комбинаций на выборке из 300 сделок,
лучшая комбинация найдена подбором, а не анализом.
```

Практически: при 300–500 сделках допустимо порядка 100–200 комбинаций за раунд.
Отсюда разбиение на три раунда по 3–4 параметра вместо одного по десяти.

## Журнал оптимизации

Для каждого раунда фиксируйте:

```
Дата, период, инструменты
Оптимизируемые параметры и диапазоны
Число комбинаций
Топ-20 с fitness и разбором составляющих
Выбранная точка и обоснование (центр плато / иное)
Результат чувствительности
Результат на VALIDATION
Решение: принять / вернуться / отвергнуть
```

Без журнала невозможно отличить «мы проверили одну гипотезу» от «мы перебрали сорок и
взяли лучшую» — а это разница между результатом и его иллюзией.
