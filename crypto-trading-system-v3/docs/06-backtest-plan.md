# План бэктеста

## Цель

Бэктест не отвечает на вопрос «сколько система заработает». Он отвечает на вопрос
**«есть ли основания полагать, что преимущество существует»** — и чаще всего честный
ответ «нет». План построен так, чтобы этот ответ было легко получить и трудно обойти.

## Настройки cTrader

| Параметр | Значение | Почему |
|---|---|---|
| Data mode | **Tick data from server** | На M1–M5 барные данные скрывают порядок внутри бара, а именно он решает, стоп или цель сработали первыми |
| Commission | Реальная у брокера | Не оценка |
| Spread | Реальный у брокера | Не фиксированный идеальный |
| Начальный депозит | Как планируется в бою | Лимиты и минимальные объёмы зависят от него |
| Режим бота | `Shadow` для исследования, `Paper` для проверки исполнения | |

**Обязательно:** перед первым бэктестом скачать тиковые данные за весь период через
cTrader → History. Бэктест на неполных данных даёт результат, который выглядит
нормально и ничего не значит.

## Периоды

Минимум — по одному репрезентативному отрезку каждого типа. Даты указаны как
ориентир для BTC/ETH; уточните под доступную историю брокера.

| Режим | Ориентировочный период | Что проверяется |
|---|---|---|
| Сильный бычий тренд | 2020-10 … 2021-04 | Трендовые стратегии зарабатывают; runner не душится |
| Медвежий тренд | 2022-01 … 2022-06 | Шорты работают; mean reversion не разоряет |
| Затяжной боковик | 2023-05 … 2023-09 | Mean reversion работает; трендовые молчат |
| Высокая волатильность | 2021-05, 2022-05 (LUNA), 2022-11 (FTX) | Размер снижается; экстремальные фильтры срабатывают |
| Низкая волатильность | 2023-08 … 2023-10 | Сжатие → расширение ловится; нет торговли в шуме |
| Крах | 2020-03-12, 2021-05-19 | Система не торгует; убытки ограничены |
| Восстановление после краха | Следующие 2 недели | Период восстановления соблюдается, возврат не мгновенный |

## Инструменты

Минимум четыре, чтобы результат не был одной ставкой:

* BTCUSD — эталон, обязателен (используется как рыночный контекст)
* ETHUSD — высокая корреляция с BTC, проверка кластеризации
* SOLUSD или аналог — высокая бета
* XRPUSD или аналог — иная динамика, проверка масштабной инвариантности

## Процедура

### Шаг 1. Разделение данных

```
│◀────── IN-SAMPLE (60%) ──────▶│◀─ VALIDATION (20%) ─▶│◀─ HOLDOUT (20%) ─▶│
   разработка и оптимизация        выбор параметров       НЕ ТРОГАТЬ
```

**HOLDOUT открывается один раз.** Если после взгляда на него параметры меняются, он
перестаёт быть holdout и становится частью обучающей выборки — навсегда. Это не
формальность: именно так большинство систем «проходят» валидацию.

### Шаг 2. Базовая линия

Сначала прогоняется `BaselineTrendStrategy` — тривиальное пересечение EMA — на тех же
данных, с теми же издержками, тем же сайзингом.

```
Если полная система не превосходит базовую линию вне выборки,
сложность не окупается и должна быть снята, а не настроена.
```

Это раздел 156 спецификации, и он выполняется буквально. Базовая линия живёт в том же
коде и в том же цикле, поэтому сравнение честное.

### Шаг 3. Прогон с реальными издержками

```
Обычные издержки → отчёт → сохранить
```

Смотреть в отчёте **в первую очередь** на:

1. **Концентрация прибыли, топ 5%.** Если > 60%, преимущество держится на выбросах
   и статистически неотличимо от везения. Отчёт печатает предупреждение сам.
2. **Матожидание без хвостовых прибылей.** Если ≤ 0, преимущества нет.
3. **Число сделок.** Менее 100 — выборка слишком мала для любых выводов.
4. **Максимальная просадка** и **длиннейшая серия убытков** — можно ли это высидеть.

Чистая прибыль смотрится **последней**. Она наименее информативна и легче всего
подгоняется.

### Шаг 4. Стресс-тест по издержкам (раздел 90)

Повторить с увеличением издержек:

```
базовые → +25% → +50% → +100%
```

В cTrader это делается изменением комиссии и спреда в настройках бэктеста.

```
Стратегия, теряющая более половины матожидания при +50%,
работает только при идеальном исполнении и должна быть отвергнута.
```

`FitnessCalculator` учитывает это автоматически, если передать ему второй отчёт.

### Шаг 5. Абляция (раздел 95)

Отключить по одному модулю и посмотреть на вклад:

| Конфигурация | Как получить |
|---|---|
| Полная система | по умолчанию |
| Без адаптации весов | `AdaptationIntervalMinutes` = очень большое |
| Без фильтра режима | `MinConfidenceToTrade` = 0 |
| Без учёта корреляции | `ClusterThreshold` = 0.99 |
| Без трейлинга | `TrailActivationR` = очень большое |
| Без частичных закрытий | `Target1ClosePercent` = минимум |
| Без ограничения цели по MFE | `MinSampleForMfeTargeting` = огромное |
| Только базовая линия | `StrategyRegistry(includeBaselineInEnsemble: true)` и отключить остальные |

Модуль, отключение которого не ухудшает результат вне выборки, — это сложность без
выгоды. Спецификация (раздел 94) требует предпочесть простое.

## Критерии отбраковки

Прогон считается **провалившимся** при любом из условий:

```
☐ Сделок < 100
☐ Матожидание ≤ 0
☐ Матожидание без хвостовых прибылей ≤ 0
☐ Концентрация прибыли (топ 5%) > 60%
☐ Profit factor < 1.2
☐ Максимальная просадка > 25%
☐ При +50% издержек теряется > 50% матожидания
☐ Более 70% прибыли из одного инструмента
☐ Не превосходит базовую линию вне выборки
```

Это не «предупреждения». Любой пункт — отказ.

## Как читать отчёт

`PerformanceReport.Render()` печатается при остановке бота. Порядок чтения:

```
1. Сделок          — достаточна ли выборка вообще
2. Концентрация    — не держится ли всё на трёх сделках
3. Без хвоста      — остаётся ли преимущество без выбросов
4. Просадка        — можно ли это пережить
5. Серия убытков   — можно ли это высидеть
6. Profit factor   — соотношение валовых
7. Матожидание     — размер преимущества на сделку
8. Чистая прибыль  — последнее и наименее важное
```

## Известные ограничения бэктеста

Честный список того, чего бэктест здесь не покажет:

* **Проскальзывание моделируется, а не измеряется.** Реальное проскальзывание на
  крипто-CFD в момент всплеска может быть кратно хуже модели. Отсюда требование
  стресс-теста.
* **Внутрибарный порядок в тиковом режиме точнее, но не идеален.** Симулятор при
  касании обоих уровней разрешает в пользу стопа — это осознанно пессимистично.
* **Отказы брокера не моделируются в cTrader.** Для этого есть режим `Paper` с
  `simulateFailures`.
* **Нет проскальзывания на частичных закрытиях** сверх смоделированного.
* **История брокера ограничена.** Для крипто-CFD глубина часто 2–3 года, чего мало
  для полного цикла.
