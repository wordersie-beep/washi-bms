# План walk-forward анализа

## Зачем

Обычная оптимизация отвечает на вопрос «какие параметры были бы лучшими на этих
данных». Это не тот вопрос. Нужный вопрос — **«работает ли процедура выбора
параметров на данных, которых она не видела»**, и отвечает на него только
walk-forward.

Разница принципиальная: walk-forward проверяет не набор параметров, а **метод их
получения**.

## Схема

```
Вся история
│
├─ Окно 1: [═══ TRAIN 90д ═══][эмбарго][═ TEST 30д ═]
├─ Окно 2:        [═══ TRAIN 90д ═══][эмбарго][═ TEST 30д ═]
├─ Окно 3:               [═══ TRAIN 90д ═══][эмбарго][═ TEST 30д ═]
├─ Окно 4:                      [═══ TRAIN 90д ═══][эмбарго][═ TEST 30д ═]
│
└─ Итог = склейка всех TEST-участков
```

Оптимизация проводится **только** на TRAIN. Параметры применяются к TEST **без
изменений**. Результат системы — это склейка TEST-участков, и ничто другое.

## Параметры схемы

| Параметр | Значение | Обоснование |
|---|---|---|
| Окно обучения | 90 дней | На M5 это ~26 000 баров — достаточно для оценки, но не настолько много, чтобы включать давно ушедший режим рынка |
| Окно теста | 30 дней | Треть от обучения; более длинный тест означает, что параметры устаревают внутри него |
| Шаг | 30 дней | Не перекрывающиеся TEST-участки, иначе одни и те же сделки попадут в итог дважды |
| Эмбарго | 2 дня | См. ниже |
| Минимум окон | 8 | Меньше — выборка окон сама по себе статистически пуста |

## Эмбарго и очистка (раздел 92)

Между TRAIN и TEST вставляется **эмбарго** — выброшенный промежуток.

Причина конкретная: сделка, открытая в последний день TRAIN, может закрыться в первый
день TEST. Её исход зависит от данных обеих выборок, и без разрыва информация из TEST
просачивается в оценку, сделанную на TRAIN.

```
Длительность эмбарго ≥ максимального времени удержания сделки.
```

При `TimeStopBarsTrend = 120` на M5 это 10 часов; двух дней с запасом достаточно.
Если время удержания увеличивается, эмбарго должно расти вместе с ним.

Дополнительно: сделки, открытые в TRAIN и не закрытые к его концу, **исключаются** из
оценки TRAIN, а не закрываются принудительно по последней цене. Принудительное
закрытие создаёт искусственные исходы, которых в реальности не было.

## Процедура

Для каждого окна:

```
1. Оптимизировать на TRAIN (протокол из документа 07, раунды 1–3)
2. Зафиксировать выбранные параметры в журнале
3. Прогнать TEST с этими параметрами, ничего не меняя
4. Записать метрики TEST отдельно
5. Сдвинуть окно на 30 дней
```

Повторить, пока хватает истории.

## Метрики

### Эффективность walk-forward

```
WFE = матожидание на TEST / матожидание на TRAIN
```

| WFE | Трактовка |
|---|---|
| > 0.7 | Метод переносится хорошо |
| 0.4 … 0.7 | Приемлемо; ожидать вне выборки примерно половину от оптимизированного |
| 0.2 … 0.4 | Слабо; вероятна существенная подгонка |
| < 0.2 | Метод не переносится |
| < 0 | TRAIN зарабатывает, TEST теряет — классическая подгонка |

### Устойчивость параметров

Проследить, как выбранные параметры меняются от окна к окну.

```
Стабильно:   1.6  1.6  1.8  1.6  1.7  1.6  1.8  1.6   ← метод находит что-то реальное
Скачет:      1.0  2.8  1.4  3.0  1.2  2.6  1.1  2.9   ← метод находит шум
```

Прыгающие параметры означают, что оптимизатор каждый раз подбирается под последние
90 дней. Итоговый результат в таком случае недостоверен, даже если WFE выглядит
прилично.

### Доля прибыльных окон

```
Прибыльных TEST-окон / всего окон
```

Ниже 50% — система не работает устойчиво, даже если суммарный результат положителен:
скорее всего, всё держится на одном-двух удачных окнах.

## Критерии прохождения

```
☐ Минимум 8 окон
☐ WFE ≥ 0.4
☐ Прибыльных окон ≥ 55%
☐ Матожидание на склейке TEST > 0
☐ Матожидание без хвостовых прибылей на склейке TEST > 0
☐ Параметры устойчивы (разброс ≤ ±25% от медианы)
☐ Максимальная просадка на склейке TEST в пределах лимита
☐ Склейка TEST превосходит базовую линию за тот же период
```

Провал любого пункта означает, что система **не идёт дальше**. Не «идёт с оговорками».

## Практическое замечание по cTrader

cTrader не выполняет walk-forward автоматически. Процедура ручная:

```
Для каждого окна:
  1. Оптимизация: задать даты TRAIN, запустить Optimization
  2. Экспортировать результаты, применить протокол отбора плато
  3. Backtest: задать даты TEST, выставить выбранные параметры, запустить
  4. При остановке бот печатает PerformanceReport — сохранить
```

Отчёт печатается в `OnStop` и содержит все нужные метрики, включая концентрацию
прибыли и матожидание без хвоста. Собирайте их в таблицу по окнам.

## Журнал walk-forward

```
Окно | TRAIN период | TEST период | Параметры | Сделок TEST | Матожидание TRAIN | Матожидание TEST | WFE
-----|--------------|-------------|-----------|-------------|-------------------|------------------|-----
  1  | ...          | ...         | ...       | ...         | ...               | ...              | ...
```

Плюс сводка: медиана и разброс каждого параметра по окнам, доля прибыльных окон,
метрики склейки.

## Частая ошибка

Соблазн после плохого walk-forward «подправить» схему: изменить длину окон, убрать
неудачный период, добавить фильтр. Каждое такое изменение делается **с знанием
результатов TEST**, то есть превращает TEST в TRAIN.

Если walk-forward провален, правильный ответ — вернуться к упрощению системы или
признать отсутствие преимущества, а не перенастраивать сам walk-forward.
