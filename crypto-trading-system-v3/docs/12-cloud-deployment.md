# Развёртывание в cTrader Cloud

## Что такое Cloud и что он требует

cTrader Cloud исполняет `.algo` в **Linux**-окружении, круглосуточно, независимо от
вашего компьютера. Из этого следуют жёсткие ограничения, и несоблюдение любого из них
даёт робота, который прекрасно работает локально и молча ломается в облаке.

| Ограничение | Как соблюдено в этом проекте |
|---|---|
| Только ссылки времени компиляции | `.algo` — **одна сборка**; ядро подключено как исходники, а не `ProjectReference` |
| Нельзя загружать сторонние .dll во время работы | Ни `Assembly.Load`, ни рефлексивной загрузки |
| Нет GUI | Ни одного обращения к `Chart`, `ChartObjects`, `Controls` |
| Нет Windows-зависимостей | `UseWPF=false`, `UseWindowsForms=false`; ядро использует только BCL |
| Файловая система недоступна | Состояние хранится в `LocalStorage`, не в файлах |
| Сеть ненадёжна как зависимость | `AccessRights.None`; внешних вызовов нет вообще |

Сериализация состояния использует `System.Text.Json` — часть BCL .NET 6, то есть
ссылка времени компиляции, а не внешняя библиотека.

## Сборка

```bash
cd crypto-trading-system-v3/src/QuantCryptoV3/QuantCryptoV3
dotnet build -c Release
```

Артефакт:

```
bin/Release/net6.0/QuantCryptoV3.algo
```

### Про структуру каталогов

```
src/QuantCryptoV3/          ← имя .algo берётся ОТСЮДА
    QuantCryptoV3/          ← здесь лежит .csproj
        QuantCryptoV3.csproj
```

SDK `cTrader.Automate` формирует имя `.algo` из имени **родительского** каталога
проекта (`_AlgoRootDirectoryName` в `cTrader.Automate.targets`). Если переместить
проект, артефакт будет назван по тому каталогу, который окажется выше — например
`src.algo`. Вложенность сохранять.

## Проверка перед загрузкой

Скрипт `scripts/cloud-preflight.sh` выполняет их все:

```bash
cd crypto-trading-system-v3
./scripts/cloud-preflight.sh
```

Он проверяет пять вещей:

| № | Проверка | Как |
|---|---|---|
| 1 | Релизная сборка без предупреждений | `dotnet build -c Release` |
| 2 | Все тесты проходят | `dotnet test` |
| 3 | Ядро не зависит от cAlgo | поиск `using cAlgo` в `src/Quant.Core` |
| 4 | Нет обращений к GUI | поиск `Chart.`, `ChartObjects`, `System.Windows`, `System.Drawing` |
| 5 | Нет файловых, сетевых операций и динамической загрузки | поиск `File.`, `HttpClient`, `WebRequest`, `Assembly.Load` |

**Важно про поиск:** проверки 3–5 обязаны смотреть только в файлы `*.cs` и исключать
каталоги `obj/` и `bin/`. Иначе они срабатывают на собственные комментарии в коде, на
отладочные `.pdb` и на `project.assets.json`, где перечислены вспомогательные
библиотеки самого SDK — те, что используются инструментами сборки, а не попадают в
`.algo`. Скрипт это учитывает; при ручном запуске `grep` добавляйте
`--include="*.cs" --exclude-dir=obj --exclude-dir=bin`.

Прогонять перед каждой загрузкой. Занимает секунды и ловит именно тот класс ошибок,
который иначе обнаруживается только в облаке.

```
1. cTrader → Algo → cBots

   (или открыть .csproj прямо в редакторе cTrader и собрать там)

```

## Настройка экземпляра

```
1. Выбрать инструмент и таймфрейм графика
   → таймфрейм графика НЕ определяет сигнальный: он задан в конфигурации (M5)
2. Выставить параметры
3. Backtest локально, чтобы убедиться в работоспособности
4. Instances → Cloud → выбрать экземпляр → Start in Cloud
```

### Рекомендуемые параметры для первого запуска в облаке

```
Режим работы                 = Shadow
Подтверждаю реальную торговлю = false
Эталонный символ             = BTCUSD
Доп. символы                 = (пусто на старте)
Сигнальный таймфрейм         = M5
Контекстный таймфрейм        = H1
Признак жизни каждые N минут = 15
Дашборд каждые N минут       = 60
Подробный журнал отказов     = false
```

**Про таймфреймы.** Сигнальный задаётся ПАРАМЕТРОМ, а не таймфреймом графика. График
на решения не влияет вообще: бот подписывается на нужные серии сам. Контекстный должен
быть медленнее сигнального — он даёт тренд более высокого порядка, и если поставить его
равным сигнальному, проверка тренда перестаёт что-либо проверять.

Набор агрегируемых таймфреймов строится автоматически: всё быстрее сигнального
отбрасывается (ни один слой такие ряды не читает), сигнальный, контекстный и
корреляционный включаются всегда. На M1 это заметная экономия работы на каждом баре.

Начинать с одного инструмента. Мультисимвольность добавляет корреляционные лимиты и
кластеризацию — их поведение стоит наблюдать отдельно, а не одновременно с первым
запуском.

## Требование круглосуточного рынка

Система спроектирована под непрерывный рынок (раздел 1 ТЗ). Инструмент с перерывами её
не ломает, но меняет её свойства:

* на открытии сессии приходит гэп, который стоп-лосс **не удерживает**;
* статистика режимов собирается по рваной серии, где «ночь» и «выходные» смешаны;
* перцентили волатильности искажены баром открытия, который систематически шире.

Бот читает недельное расписание у платформы (`Symbol.MarketHours.Sessions`) и печатает
вердикт при старте:

```
BTCUSD: круглосуточно (168 ч/нед) | рынок ОТКРЫТ
Все инструменты торгуются круглосуточно — режим 24/7 доступен.
```

Допуск на «почти круглосуточный» рынок — 8 часов в неделю: у многих брокеров крипта
закрывается на несколько минут в сутки на расчёт свопов, и считать такой инструмент
непригодным было бы неверно.

**Плановый перерыв отличается от потери данных.** Разрыв в барах, который объясняется
закрытием рынка, не понижает оценку качества данных. Без этой поправки инструмент с
перерывом отвергался бы после каждого открытия сессии: разрыв в десятки интервалов
читается как сбой подачи. Пока рынок закрыт, новые входы не рассматриваются, а признак
жизни прямо называет причину и время до открытия.

Расписание, которое платформа не сообщила, трактуется как круглосуточное сознательно:
иначе отсутствие данных превращалось бы в предупреждение о проблеме, которой может не
быть.

## Мультисимвольная конфигурация

```
Инструмент графика = BTCUSD
Доп. символы       = ETHUSD,SOLUSD,XRPUSD
Эталонный символ   = BTCUSD
```

Бот подписывается на бары и тики всех перечисленных инструментов через
`MarketData.GetBars` и `Symbol.Tick`. Эталон добавляется автоматически, даже если им
не торгуют: он нужен для рыночного контекста.

**Про нагрузку.** Каждый инструмент — это 6 таймфреймов × набор индикаторов. Четыре
инструмента — 24 серии. Всё инкрементально и обновляется только на закрытии бара, но
разумный потолок для облака — 4–6 инструментов. Тиковый путь намеренно лёгкий: только
проверка котировки, статистика спреда и обновление MAE/MFE.

## Прогрев истории

При старте бот прогоняет историю через движок (`WarmUpHistory`), чтобы индикаторы и
перцентили были готовы к первому решению, а не набирались неделю на живом рынке.

Требуется:

```
MinBarsBeforeTrading = 200 баров на сигнальном таймфрейме (M5 → ~17 часов, M1 → ~3.5 часа)
MinBarsPerTimeframe  = 60 баров на контекстном (H1 → 60 часов)
```

Если истории не хватает, система честно отказывается торговать с причиной
`DataQuality: insufficient history` — это видно в журнале.

**Прогрев не принимает решений.** Исторические бары проходят только тот участок цикла,
который накапливает состояние рынка: агрегацию, индикаторы, признаки, классификацию
режима. Всё, что обращается наружу — оценка риска, сопровождение позиций, сверка с
брокером, попытки входа и запись состояния — на прогреве не выполняется.

Разделение обязательно, а не косметично. Без него прогрев пятисот баров означает
пятьсот оценок риска по ценам двухдневной давности, сверку с брокером на историческом
времени и — что хуже всего — дневную точку отсчёта, привязанную к историческому дню.
Дневной лимит убытка после этого считался бы от капитала, которого на счёте никогда
не было.

## Мониторинг

В облаке доступен только вывод `Print`. Мониторинг двухуровневый.

### Признак жизни

Раз в `HeartbeatIntervalMinutes` печатается одна строка:

```
[жив] 12:30:00Z | BTCUSD баров 1204 TrendUp(68%) | риск Normal | позиций 0 | решений 485 (принято 0) | чаще всего: LowRegimeConfidence 33 %
```

Он существует потому, что **правильно молчащая система неотличима от мёртвой**. На
настройках по умолчанию отклоняется более 99% сигналов, а отказы пишутся в лог только
при смене причины — и лог может быть пустым часами. Без признака жизни единственный
способ отличить работающего бота от упавшего — ждать сделки, которой может не быть
неделю.

Строка отвечает на четыре вопроса сразу: жив ли процесс, хватает ли истории, какова
постура риска и почему нет сделок. Отсутствие строки дольше интервала — единственный
надёжный признак того, что что-то сломалось.

### Дашборд

Печатается раз в `DashboardIntervalMinutes` и содержит:

```
капитал, постура риска, просадки по горизонтам
теплота портфеля и список позиций
режимы по инструментам
состояния и веса стратегий
статистика, калибровка, качество исполнения
сводка причин отказа
```

### На что смотреть

```
Ежедневно:  признак жизни печатается без пропусков; нет исключений; постура риска осмысленна
Еженедельно: ECE калибровки; качество исполнения; распределение причин отказа
Ежемесячно:  сравнение с бэктестом; полный отчёт; журнал ценности фильтров
```

## Сохранение состояния в облаке

`LocalStorage` с областью `Instance`. Область выбрана намеренно: состояние принадлежит
конкретному экземпляру. Общая область означала бы, что два экземпляра на разных
инструментах перетирают состояние друг друга.

Состояние сохраняется на каждом закрытии сигнального бара. Сбой записи **не
останавливает торговлю**: потеря снимка — неприятность, исключение в торговом цикле —
авария.

## Перезапуск и обновление

При остановке и повторном запуске экземпляра в облаке:

```
1. Восстанавливается состояние из LocalStorage
2. Позиции берутся ОТ БРОКЕРА, контекст — из состояния
3. Позиции без контекста → АВАРИЙНАЯ ОСТАНОВКА, требуется вмешательство
```

При **обновлении версии** бота с открытыми позициями схема состояния может измениться.
`StateSerializer` отбрасывает состояние другой версии схемы целиком — и тогда сработает
сценарий «позиции есть, контекста нет».

```
Обновлять версию бота только при отсутствии открытых позиций.
```

## Известные ограничения облака

* **Нет доступа к файловой системе** — экспорт журнала сделок возможен только через
  `Print` и копирование из лога.
* **Логи ограничены по объёму** — при `VerboseJournal = true` они заполняются быстро.
* **Нет внешних уведомлений** — `AccessRights.None` исключает и сеть, и e-mail.
  Мониторинг ручной, через лог.
* **Перезапуск облачного экземпляра сбрасывает процесс** — но не `LocalStorage`.
* **Время сервера** — вся логика работает в UTC (`Server.TimeInUtc`), что устраняет
  проблемы часовых поясов и перехода на летнее время.
